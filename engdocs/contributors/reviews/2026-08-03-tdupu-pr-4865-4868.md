## Decision summary

### #4865: approve

The one-line behavior change is correct and bounded. The CLI-local resolver now
admits dot-qualified candidates into `resolvePoolInstance`, matching the shared
resolver's existing `ContainsAny(input, "/.")` gate. The callee still requires an
exact configured qualified-name prefix, a positive integer suffix, an expandable
non-singleton pool, and an in-bounds slot (`cmd/gc/cmd_agent.go:301-352`). Dot-
qualified non-instance names therefore continue to fall through.

The alias-deferral gotcha was checked through the runtime boundary. The test
session bead deliberately has no persisted alias and carries only `template`,
`session_name`, and `pool_slot`. `lookupPoolSessionNameCandidates` recovers the
binding-qualified instance from `pool_slot` even while `Info.Alias == ""`
(`cmd/gc/session_name_lookup.go:768-857`). A disposable assertion verified that
`doSlingNudge` reached `runtime.Provider.IsRunning` for the concrete session
`testpack__worker-session-test`. The command then delivered the nudge to
`testpack.worker-1` without taking
the former “not found in config” path.

The author tests pass at the exact head and after applying the PR to the tested
base:

```text
go test ./cmd/gc -run 'TestResolveAgentIdentityResolvesBindingQualifiedPoolInstance|TestDoSlingNudgePoolMemberBindingQualifiedCityScope' -count=1
ok github.com/gastownhall/gascity/cmd/gc

go test ./cmd/gc -run 'TestResolveAgentIdentity|TestDoSlingNudgePool' -count=1
ok github.com/gastownhall/gascity/cmd/gc
```

I found no new correctness issue. Consolidating the CLI-local and shared
resolvers would prevent future drift, but that is the issue's explicitly
separate candidate B and is not required for this focused fix.

### #4868: request changes

The premise is real, but the fix preserves neither demand nor ownership for the
work that caused the resume. The new guard skips the only request carrying
`WorkBeadID`, `SessionBeadID`, priority, pack, workspace, and brain lineage
(`cmd/gc/pool_desired_state.go:168-229`). It does not emit a replacement request
or detach the work from the asleep session.

Two exact-head adversarial tests reproduced the consequences:

1. With `wake_mode = "fresh"`, an asleep session owning in-progress `w1`, and
   `min_active_sessions = 0`, `ComputePoolDesiredStates` returns no desired state.
   The assigned work creates no scale-check demand, so the agent never wakes.
2. With the same state and `min_active_sessions = 1`, the minimum-fill path emits
   one anonymous `Tier:"new"` request with empty `WorkBeadID`. A fresh session can
   start, but it has no ownership of `w1`.

The downstream lifecycle does not repair this split:

- `releaseOrphanedPoolAssignments` treats the still-open asleep session as the
  owner and refuses to clear the assignment (`cmd/gc/pool_session_name.go:140-186`).
- The session close guard refuses to close a session while open or in-progress
  work remains assigned (`cmd/gc/session_work_guard.go:51-81`).
- Minimum fill counts accepted requests, not existing open asleep rows, and
  emits an anonymous floor request (`cmd/gc/pool_desired_state.go:467-539`).

The author test proves only that the stale resume disappears and a floor session
appears. It does not assert that the replacement carries the assigned bead or
that the old assignment becomes claimable. The focused suite and tested-base
integration suite pass because neither includes those delivery invariants.

The exact-head author test and the tested-base integration suite were rerun with:

```text
go test ./cmd/gc -run '^TestComputePoolDesiredStates_FreshWakeSkipsAsleepResume$' -count=1
ok github.com/gastownhall/gascity/cmd/gc

go test ./cmd/gc -run 'TestComputePoolDesiredStates|TestBuildPoolDesiredStatesHonorsNestedMaximum|TestBuildPoolDesiredStatesRejectsNestedCapBeforeCreation' -count=1
ok github.com/gastownhall/gascity/cmd/gc
```

The disposable exact-head assertions failed with the two expected mechanisms:

```text
TestComputePoolDesiredStates_FreshWakePreservesAssignedWorkWithoutMin:
fresh wake dropped all demand for assigned in-progress work: []main.PoolDesiredState(nil)

TestComputePoolDesiredStates_FreshWakeMinFillCarriesAssignedWork:
replacement request has Tier:"new", WorkBeadID:"", FloorGuarantee:true; want WorkBeadID "w1"
```

The fix should make the replacement atomic from the desired-state consumer's
perspective: either emit a fresh request carrying the original work identity and
retire/reassign the stale owner through the established session front door, or
perform an equivalent typed lifecycle transition before suppressing the resume.
Tests must cover both zero and nonzero minimums and prove the original bead is
claimable by the replacement session.

Thanks for isolating the CLI-local resolver drift and covering both the direct
resolver and sling-nudge path. I verified the exact head

### Draft for #4868

Thanks for pinning the stale asleep-resume loop and keeping live sessions and
resume-mode agents unchanged. The premise is valid, and the new guard does stop
the doomed resume at
`5b5f144ed3bf79a99b9f6ba7473a83b20dc6b0f1`.

I would request one ownership fix before merge. Skipping the resume also drops
the only desired-state request carrying the assigned work bead. With no minimum,
the result is empty and the in-progress bead never wakes anything. With a
minimum of one, the replacement is an anonymous floor session, while orphan
release preserves the old assignment because its asleep session row is still
open. Please make the fresh replacement carry and claim the original work, and
retire or detach the stale owner through the normal session lifecycle. Add
regressions for both `min_active_sessions = 0` and `1` that prove the original
bead is claimable by the replacement.
